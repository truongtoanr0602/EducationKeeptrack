# T10 — Cashflow and obligation-period statistics

Ticket: [#11](https://github.com/truongtoanr0602/EducationKeeptrack/issues/11).
Review baseline: `e4d8e016ca4592b1374a06f48a100d584eba3efb`.

The approved scope is statistics within each class's existing tuition workspace,
with two views: inclusive actual receipt dates in Vietnam and exact obligation
month. Tests use the approved system API/real PostgreSQL and desktop/mobile browser
boundaries. Existing unrelated untracked files remain outside this change.

## Behavior

- A 500,000 receipt on November 5 paying October debt appears once in November
  cashflow and reduces October debt, with receipt/period reconciliation detail.
- Cashflow sums only active receipt amounts, independent of allocation count;
  replacement actual dates move cashflow between months and cancellation removes
  current amounts while original history remains available.
- Period statistics show adjusted fees, gross allocation, paid funds excluding
  holds, held money and debt; unallocated credit remains outside period payments.
- One existing repeatable-read Billing snapshot supplies each report's details,
  totals and ledger version; no new financial tables or derived cached reports.
- Strict date/month filters, teacher/class isolation, exact large monetary values,
  service-expiry read access and anonymous denial have API coverage.
- Tests distinguish October UTC entry time from November Vietnam actual receipt
  dates and verify inclusive first/last days. Pending/missing-rate reports retain
  explicit status instead of claiming complete debt.
- Browser checks compare totals to detailed rows, drill down to allocations,
  preserve class navigation, refresh cancellation, retain filters across reload,
  hide totals on load failure and check mobile overflow.

Reserve redemption is not implemented yet. Cashflow counts only actual receipt
records, so future redemption must remain a separate financial operation.

## Standards

Owner-scoped reads, module contracts, exact money, snapshot consistency and UI
request sequencing follow the existing design. One optional observation remains:
split the two renderers out of `CashflowStatistics.tsx` if the UI grows further.

counts only active receipt records, never allocation or adjustment operations.
